# 知行案例来源与改造模块

版本：v0.1

## 1. 模块定位

这个模块负责把知乎或全网的真实工程内容，转化为知行可复现、可练习、可验证的学习案例。

```text
真实来源
  -> 来源摘录与问题模式
  -> AI 改造方案
  -> 可复现案例
  -> 用户实践证据
```

它不是简单的内容抓取器，也不是让模型自由生成题目。它必须回答：案例参考了什么、AI 改造了什么、哪些结果来自实验、哪些结论仍待核验。

## 2. 一期边界

一期准备三个共享引擎的 MySQL 案例：慢查询与联合索引、死锁与锁等待、深分页优化，并允许人工确认 AI 改造结果。慢查询是主 Demo，其他案例用于验证案例引擎的可复用性。

### 一期需要做

- 接收学习目标并匹配已有案例模板；
- 接收知乎或全网检索得到的来源摘要和链接；
- 提取来源中的工程问题、约束、排查路径和权衡点；
- 生成可编辑的案例草稿，而不是直接发布；
- 允许 AI 先生成案例，但必须经过校验 Agent 审核后才能进入学习流程；
- 为案例生成固定 SQL、DDL、种子数据、错误尝试和验证条件；
- 保存来源、改造记录、实验数据和用户证据之间的关联。

### 一期不做

- 自动抓取全网并直接生成可用案例；
- 把搜索摘要当作完整文章或权威结论；
- 复制知乎文章全文；
- 用 AI 编造生产事故、作者经历、性能数字或引用；
- 根据用户收藏、简历和长期画像自动推荐案例；这些属于 OAuth 和个性化推荐阶段。

## 3. 输入模型

输入分为“进入一期就需要”和“后续增强输入”，不同输入不应混成一个无结构的 Prompt。

### 3.1 学习目标输入

用户主动输入想学习的内容，是案例推荐的起点。

| 字段 | 示例 | 必填 | 用途 |
| --- | --- | --- | --- |
| `goal_text` | 我想学习 MySQL 慢查询优化 | 是 | 匹配技术领域和案例主题 |
| `desired_outcome` | 能定位问题并验证索引优化是否有效 | 否 | 选择案例完成标准 |
| `available_time` | 30 分钟 | 否 | 后续筛选案例长度 |
| `current_level` | 会写 SQL，但不会读 EXPLAIN | 否 | 后续调整提示起点 |

一期只要求 `goal_text`。推荐结果必须标记为“基于当前案例目录的推荐”，不能伪装成完整个性化判断。

### 3.2 来源输入

来源可以来自知乎搜索、全网搜索或人工提供的 URL。

| 字段 | 示例 | 必填 | 用途 |
| --- | --- | --- | --- |
| `source_type` | `zhihu_search` / `global_search` / `user_url` | 是 | 标记来源渠道 |
| `source_id` | 知乎 `ContentID` | 来源可提供时必填 | 稳定追溯原始内容 |
| `query` | MySQL 联合索引 等值 范围 ORDER BY | 检索来源必填 | 保留检索 provenance |
| `title` | MySQL EXPLAIN 执行计划深度解析 | 是 | 来源展示和人工筛选 |
| `author` | 作者名称 | 来源可提供时必填 | 来源展示 |
| `url` | 原文 URL | 是 | 打开原文和文章引用 |
| `excerpt` | CLI 返回的摘要片段 | 是 | 提取问题模式，不代表全文 |
| `retrieved_at` | 采集时间 | 是 | 判断数据新鲜度 |

### 3.3 案例改造约束

这是用户或系统为 AI 改造设定的边界，防止模型只追求“故事好看”。

| 字段 | 示例 | 必填 | 用途 |
| --- | --- | --- | --- |
| `technology` | MySQL 8 | 是 | 限定技术栈 |
| `case_theme` | 慢查询与 EXPLAIN | 是 | 限定工程问题 |
| `difficulty` | beginner-intermediate | 否 | 控制问题复杂度 |
| `practice_duration` | 20 分钟 | 否 | 控制实验规模 |
| `environment` | Docker 本地实验 | 是 | 保证可复现和隔离 |
| `preserve_constraints` | 筛选语义不变、保持排序 | 是 | 防止通过改需求伪造优化 |
| `allowed_changes` | 可改 SQL 和索引，不改业务结果 | 是 | 限制修复范围 |

### 3.4 案例草稿输入

AI 生成或人工补充的案例草稿必须拆成结构化字段：

- `context`：业务背景和用户角色；
- `symptom`：用户能观察到的现象；
- `initial_artifacts`：问题 SQL、表结构、日志或固定说明；
- `user_action_options`：用户可以先执行的动作，不预先给出唯一答案；
- `failure_attempt`：至少一个可解释的不充分尝试；
- `repair_candidate`：候选修复及其假设；
- `required_evidence`：EXPLAIN、基准和结果集一致性；
- `acceptance_rules`：何时支持、何时证据不足、何时语义变化；
- `residual_risks`：写入成本、数据分布、统计信息和环境差异。

### 3.5 后续增强输入

以下输入不作为一期进入条件，但模块接口需要预留：

- OAuth 授权后的知乎收藏、关注和本人创作；
- 用户提供的简历、自述和历史学习记录；
- 用户正在处理的真实问题和脱敏后的日志；
- CLI 自动采集的 SQL、EXPLAIN、终端输出和配置；
- 用户对案例难度、来源质量和推荐结果的反馈。

这些数据必须明确授权范围、脱敏状态和来源类型，不能和一期的公共来源或合成实验数据混为一谈。

## 4. AI 生成与校验门禁

AI 生成案例是允许的，但案例不能以 `generated` 状态直接展示给学习者。生成链路至少经过以下状态：

```text
source_collected
  -> case_generated
  -> deterministic_checked
  -> agent_reviewed
  -> human_confirmed
  -> learner_available
```

### 4.1 确定性检查

这部分不交给模型判断：

- 案例结构符合 Schema，必填字段、状态、证据类型和来源 ID 完整；
- SQL、DDL 和验证命令必须在隔离的 MySQL Lab 中实际执行，而不是只通过语法检查；
- 种子数据可以产生预期的症状、失败尝试和最终对比；
- 修复前后查询结果集语义一致，不能通过删条件或缩小范围制造成功；
- 性能数字都带有 `scenario_seed`、`user_input` 或 `cli_capture` 来源标记；
- 内容中不存在 Access Secret、数据库密码、真实连接串等敏感信息。

### 4.2 校验 Agent 审核

校验 Agent 输出结构化审查结果，不直接悄悄改写案例：

- **来源一致性**：哪些内容来自原文，哪些是 AI 改造，哪些是实验生成；
- **工程合理性**：症状、假设、修复、证据和结论是否前后一致；
- **教学可行性**：用户是否有至少一个可执行的处理入口，失败尝试是否可解释；
- **证据充分性**：每个关键结论是否关联必要证据，是否存在未经验证的绝对表述；
- **难度与时长**：案例是否适合目标用户和预计实践时间；
- **来源风险**：是否把搜索摘要当全文、复制原文或把作者观点冒充实验事实。

审核结果只能是 `pass`、`needs_revision` 或 `reject`，并附带问题等级、字段路径和依据。`needs_revision` 返回生成器修改后重新审核，不能由人工直接忽略阻断项。

### 4.3 人工确认

一期允许 AI 生成和校验 Agent 审核通过后进入人工确认页。人工只需要确认来源、约束和案例目标；确认后才进入学习者可见的案例目录。后续可以自动化低风险案例，但不能删除追溯和撤回状态。

### 4.4 验证失败与兜底

验证失败后不直接把失败案例展示给学习者，也不无限重试生成。系统先区分失败类型：

- `case_invalid`：SQL、DDL、种子数据、状态转移或验收规则本身不成立；案例进入 `needs_revision`，保留校验日志和失败输出；
- `environment_unavailable`：Docker、MySQL 或依赖服务不可用；案例不判定为无效，切换到已验证的固定实验快照；
- `source_insufficient`：来源不足、引用不对应或无法支撑关键断言；案例退回来源筛选，不允许模型自行补写事实。

兜底按以下顺序执行：

1. 当前案例重试一次确定性的环境初始化或使用同版本的已验证实验快照；
2. 仍失败则回退到最近一个 `learner_available` 的已验证案例模板；
3. 没有可回退案例时显示“案例准备中”，保留学习目标和失败原因，不生成看似完整但不可运行的案例。

兜底事件必须记录 `fallback_reason`、原案例版本、回退案例版本和验证报告，不能把回退结果伪装成新案例已经验证成功。

## 5. 输出与追溯

模块至少输出四类对象：

| 输出 | 内容 | 是否允许直接进入学习流程 |
| --- | --- | --- |
| `source_extract` | 来源 ID、链接、摘要、问题模式和引用片段 | 否，需人工或规则筛选 |
| `case_draft` | AI 改造后的案例草稿、变更说明和审核结果 | 否，需通过校验并人工确认 |
| `case_fixture` | SQL、DDL、种子数据、错误尝试和验证脚本 | 是，但必须标记实验环境 |
| `provenance_map` | 来源字段 -> 改造字段 -> 实验字段 -> 文章断言 | 是，作为页面和文章的追溯依据 |

### 5.1 Tutor 参考卡改写

已核验来源可以被改写为面向当前学习节点的短参考卡，而不是直接复制文章内容。改写只承担“解释原理、提供排查视角或提示权衡”的作用，不能替代用户实验或案例状态机判定。

每张卡至少保存：

- `source_id`、标题、作者、原文 URL 和允许展示的摘录；
- `stage` 与 `current_question`，说明它只服务哪个判断节点；
- `adapted_guidance` 与 `adaptation_version`，明确它是基于来源的改写；
- `supported_claims`，逐条列出改写所依赖的来源断言；
- `evidence_boundary`，声明哪些性能、结果集或修复结论仍必须由 Docker Lab 证明。

卡片页面必须显示来源入口与“基于来源改写”标识。若来源只保留搜索摘要、原文未核验、或摘要不足以支持改写断言，则只能显示原文入口和采集信息，不能生成解释性参考卡。

AI 改造必须同时输出 `preserved_from_source`、`changed_by_ai`、`generated_for_lab` 和 `needs_verification` 四类变更记录。任何没有来源或实验支持的内容，都不能标记为真实事实。

## 6. MySQL 案例的一期输入示例

```json
{
  "goal_text": "我想学习 MySQL 慢查询优化",
  "source_refs": [
    {
      "source_type": "zhihu_search",
      "source_id": "待填 ContentID",
      "query": "MySQL EXPLAIN key rows Extra 优化",
      "url": "待填 URL"
    }
  ],
  "constraints": {
    "technology": "MySQL 8",
    "environment": "docker",
    "preserve_constraints": ["筛选语义不变", "按 created_at 倒序"],
    "practice_duration_minutes": 20
  }
}
```

示例中的 `待填` 字段不能在生成案例前被模型自行补齐；它们必须来自知乎 CLI、人工输入或实验环境。

## 7. 一期验收

- 输入一个学习目标可以匹配 MySQL 案例，但不依赖 OAuth；
- 每个案例至少关联一条知乎或全网来源，且可打开原文；
- 页面能区分来源原文、AI 改造和本地实验数据；
- AI 改造结果可以被人工修改、拒绝或重新生成；
- AI 生成案例必须经过确定性检查和校验 Agent 审核，审核结果可追溯；
- 确定性检查必须实际运行实验；环境失败和案例失败有不同状态，并能进入固定兜底路径；
- 案例中的性能数字只能来自固定实验或用户证据；
- 删除来源后，相关案例字段和文章断言会被标记为待确认；
- 从案例草稿能追溯到最终证据和文章中的引用。
