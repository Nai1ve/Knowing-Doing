# 知行 MySQL 案例包与对话运行时

版本：v0.1

## MVP 决策

MVP 支持三个 MySQL 学习案例，共用一个 MySQL Lab、案例引擎、Tutor 对话协议和证据模型：

| 案例 ID | 案例 | 训练重点 | 主证据 |
| --- | --- | --- | --- |
| `mysql-order-list-index-001` | 慢查询与联合索引 | EXPLAIN、函数条件、联合索引和结果集验证 | SQL、EXPLAIN、基准、结果集 |
| `mysql-deadlock-lock-order-001` | 死锁与锁等待 | 止损与根因区分、事务顺序、并发验证 | 事务 SQL、死锁日志、锁等待、并发复测 |
| `mysql-deep-pagination-001` | 深分页优化 | OFFSET 成本、游标分页、排序稳定性和产品取舍 | SQL、EXPLAIN、基准、分页结果 |

慢查询案例是三分钟主 Demo。另两个案例必须能进入同一训练台并走到“结论待确认”或“已验证 / 已解决”，以证明系统不是单一的静态剧本。

## 已冻结的 MVP 闭环

```text
用户输入学习目标
  -> 系统推荐预置案例
  -> 展示症状、约束、表结构和现有索引
  -> 用户索取并从脱敏慢日志定位目标语句
  -> 展示固定种子的只读 SQL 参考与空白执行区
  -> Tutor 主动围绕当前证据缺口引导下一步
  -> 用户讨论、运行 SQL、获得原始 Lab 证据并先自行观察
  -> Tutor 按用户意图、现有证据和缺失条件动态继续
  -> 满足根因、修复、语义与性能验证条件后进入 resolved
  -> 异步生成可编辑笔记大纲
  -> 用户按需生成完整文章初稿，人工审核后再考虑发布
```

上图定义的是闭环与边界，不是线性剧本。用户可以从任意可执行操作开始、直接提出方案或走不同尝试路径；只有环境、业务约束、原始证据、状态通过条件和完成判定是确定性的。

## 共同内核：讨论、回答与尝试

案例的核心循环不是先答对理论题，而是：

```text
案例上下文
  -> 用户说明判断或准备采取的动作
  -> Tutor 根据当前事实回应
  -> 用户执行或提交一次尝试
  -> 系统保存原始证据并校验
  -> Tutor 根据结果发起下一轮讨论
```

用户可以直接提出修复方案，并从任意可执行操作开始。系统不阻止尝试，但没有满足证据条件时，不能把尝试标为“已解决”。案例的状态与验证规则固定，用户路径和 Tutor 具体追问不固定；Tutor 只能依据当前输入、已有证据和缺失条件引导下一步。

根因有证据支持、修复已执行、结果集语义与性能证据均通过后，实践任务进入 `resolved` 并可直接结束。复盘、笔记和知乎文章属于解决后的按需沉淀流程，不是 `resolved` 的前置条件，也不能改变已验证的完成判定。

### 事件模型

每轮交互都追加事件，不从聊天文本反推事实：

| 事件 | 产生者 | 保存内容 |
| --- | --- | --- |
| `case_presented` | 系统 | 案例版本、初始材料和环境标签 |
| `log_statement_selected` | 用户 | 候选语句 ID、是否匹配、当前日志定位误选次数 |
| `user_message` | 用户 | 原始问题、判断或操作意图 |
| `tutor_reply` | Tutor | 回应、追问、提示级别、依据的证据/来源 ID |
| `attempt_submitted` | 用户 | SQL、DDL、事务步骤或分页方案及说明 |
| `evidence_captured` | 用户/实验环境 | 原始 EXPLAIN、日志、基准、结果集校验 |
| `attempt_reviewed` | 规则/校验 Agent | 支持、不支持或证据不足，以及具体依据 |
| `stage_transitioned` | 状态机 | 前后状态、满足的条件和关联事件 ID |
| `note_outline_generated` | 模型 / 模板 | 大纲、关联事件与证据 ID、生成方式、待用户编辑状态 |
| `article_draft_generated` | 用户触发的模型 | 完整初稿、段落对应的证据与来源 ID、人工审核状态 |

### Tutor 回应协议

Tutor 每次只处理当前讨论，不得自行执行修改、伪造证据或直接推进状态。输出必须可被训练台展示和审计：

| 字段 | 含义 |
| --- | --- |
| `response` | 针对用户本轮输入的解释或回应 |
| `intent` | `clarify`、`triage`、`evidence_request`、`attempt_review`、`tradeoff`、`reflect` |
| `current_gap` | 当前还缺什么事实或验证 |
| `next_question` | 一次最有价值的追问 |
| `suggested_actions` | 1 至 3 个可执行动作，不能伪装成已执行 |
| `evidence_refs` | 支撑本轮说法的用户证据 ID |
| `source_refs` | 可选的知乎/全网来源 ID 与“为什么当前读它” |

当用户提出直接修复方案时，Tutor 的默认行为是“承认这是一个可尝试的方向 -> 要求说明验证方式 -> 等待尝试结果”，而不是把方案判成正确或错误。

当用户成功选中慢日志中的目标语句并获得可运行副本后，Tutor 必须主动发起下一轮引导：说明当前尚未获得执行计划等验证证据，并只提出一个面向下一步验证的开放问题。它不得自动执行 SQL、自动提交假设，或将完整 `EXPLAIN` 语句当作默认答案填入编辑器。

此时工作台分为两个稳定区域：已选 SQL 以只读参考形式展示，保留语句来源与演示环境标识；独立的执行编辑器初始为空，由用户自行编写验证命令。用户明确索取示例或触发对应提示阈值后，Tutor 才可将最小命令模板放入编辑器，且仍须由用户确认执行。

初始 `EXPLAIN` 执行成功后，工作台先展示完整原始输出和解析出的 `type`、`key`、`rows`、`Extra` 字段，并生成证据卡。Tutor 此时只邀请用户说明自己观察到的异常或不确定点，不立即解释字段含义、判定索引是否失效或建议修复；收到用户观察后，才将其与当前假设和下一步尝试关联。

进入 `resolved` 后，系统异步从当前 `PracticeRun` 的问题、假设、SQL、失败尝试、Lab 证据、Tutor 提示、知乎来源与残余风险生成可编辑笔记大纲，并追加 `note_outline_generated`。大纲生成不会延迟或撤销 `resolved`；模型不可用时使用同一证据链生成结构化模板，并标明生成方式。训练台保持在解决结果页，只显示笔记已生成状态和进入入口，不自动跳转。用户可直接结束训练、主动打开并编辑笔记，或主动发起一篇知乎文章完整初稿。

笔记大纲固定使用以下工程复盘骨架，而不是泛化知识摘要：

1. 问题与约束：症状、业务语义和环境边界；
2. 采取过的判断：用户假设、关键追问和判断变化；
3. 执行与证据：慢日志、SQL、EXPLAIN、基准和结果集校验；
4. 失败尝试：尝试内容、不足之处和由此排除的方向；
5. 最终方案与残余风险：根因、修复、验证结论、索引代价与待跟进项。

每一部分都必须关联至少一个事件、Docker Lab 证据或知乎来源；没有素材的部分保留待补状态，不能由模型虚构补齐。

用户从笔记页发起文章生成时，系统以当前笔记、关联事件、Lab 证据和已核验来源生成完整可编辑初稿，并追加 `article_draft_generated`。文章中的事实性断言必须保留证据或来源引用；演示数据、用户实测和来源观点必须明确区分。正文在相关段落提供轻量来源或证据入口，文末汇总完整来源列表；初稿始终标记为待人工审核，不自动发布到知乎。

### 统一问题节点

三个案例共用以下讨论节点，但用户可以从任意可执行动作开始：

1. 当前看到了什么现象？
2. 现在最优先处理什么？是否需要先止损？
3. 用什么证据支持或推翻当前判断？
4. 准备执行什么最小尝试？
5. 尝试结果改变了什么判断？
6. 如何验证修复没有改变业务语义？
7. 方案还有什么代价、边界或后续风险？

## 工作台与 MySQL Lab 执行边界

一期 MySQL 训练台包含受控的 SQL 执行窗口。它不是通用 IDE 或本机终端，而是唯一连接到知行 Docker Lab 的案例操作面：

```text
用户在工作台说明下一步
  -> 工作台提供可编辑 SQL/命令草稿和按需示例
  -> 用户在内嵌 SQL 窗口执行到知行 Docker Lab
  -> 工作台获取原始输出
  -> 工作台保存证据，Tutor 基于结果继续讨论
```

- Docker Lab 是 MVP 必须交付的受控环境：平台预先提供一个固定 MySQL 8 Docker，知行通过人工 migration 维护三个 schema、种子、案例脚本、预期失败尝试、基准命令和一键重置；应用不创建或销毁容器；
- SQL 执行窗口只连接当前案例的 Docker MySQL，Web 不读取用户本地数据库凭据，也不提供任意主机连接能力；
- 工作台显示当前目标、约束、用户输入和可编辑的 SQL/命令草稿；
- 用户说“查看执行计划”时，Tutor 先询问“自己写还是看最小示例”；只有用户要求或连续无进展时才给出示例；
- 空 SQL、无效 EXPLAIN 格式等操作错误提供格式修正和“使用当前 SQL”的明确选择，不伪造证据；
- 工程判断不同于格式错误。用户直接提出“加索引”可以作为尝试方向，但必须说明或提交验证结果；
- `attempt_submitted` 只代表用户准备或提交了操作，SQL 窗口返回的原始输出产生 `evidence_captured`；来自 Docker Lab 的输出可参与“已验证”判定；
- 用户也可以粘贴任意外部输出，但系统必须标记为 `external_unverified`，只用于讨论，不能单独证明案例修复成功；
- 所有用户输入、采用的示例、Lab 输出、外部输出、报错和 Tutor 提示层级都进入笔记素材池。

慢查询案例选错脱敏日志中的语句时，Tutor 只要求用户说明该语句与订单列表 p99 症状的关联，不直接揭示答案。连续两次选错后，系统才定向引导用户检查与 `orders`、订单列表筛选和高耗时相对应的 `SELECT`。这使用案例专属的日志定位误选计数，不消耗通用的三次无进展提示额度。

死锁案例需要两个命名 SQL 会话，以便用户显式控制事务 A/B 的执行顺序；深分页和慢查询使用单会话 SQL 窗口即可。Docker Lab 不可用时进入 `environment_unavailable`：工作台显示启动/重置说明，并且只能回放同版本、已验证的实验快照。后续可以扩展为用户授权的 CLI 自动采集，但自动采集不能改变“原始输出可查看、来源可追溯、用户可拒绝采集”的规则。

## 案例一：慢查询与联合索引

学习目标：`我想学习 MySQL 慢查询优化`。

案例入口只呈现订单列表查询变慢、业务约束、表结构和现有单列索引；不直接呈现 `DATE(created_at)` 条件或原始慢 SQL。用户可先提出索引方案、索取慢日志，或要求解释表结构。系统先给一段脱敏慢日志，用户须选中与症状对应的 SQL；随后才提供固定种子数据的可运行副本。Tutor 再将“索引可能失效”落实为执行计划证据；最终比较时间条件改写、联合索引、扫描成本、耗时和结果集。

## 案例二：死锁与锁等待

案例呈现两个批处理任务偶发失败或长时间等待。入口问题是：`你现在准备如何处理？`

- 用户选择回滚、重试、查看死锁日志、调整事务或统一访问顺序都可以作为第一步；
- Tutor 先区分临时止损与根因修复：重试可以恢复当前请求，但不能解释死锁为什么发生；
- 用户需要比较两组事务 SQL、锁定资源顺序和死锁/锁等待证据；
- 最终尝试是统一资源访问顺序，必要时缩小锁范围或补充索引；
- 验证必须在并发复测下确认死锁消失，且没有订单遗漏、重复更新或无界重试。

关键追问：`当前动作是在止损，还是在修复根因？要区分两者，还缺少哪一份锁证据？`

## 案例三：深分页优化

案例呈现订单列表在很后页码变慢，且必须保持排序与分页结果的可解释性。入口问题是：`你准备先怎么处理？`

- 用户可以运行 EXPLAIN、加索引、缩小页数、提出游标分页或要求更多上下文；
- Tutor 先确认产品约束：是否必须跳转任意页、数据新增时允许何种一致性、排序是否唯一稳定；
- 对“只加索引”的方案，Tutor 追问数据库是否仍需跳过大量 OFFSET 行；
- 用户比较 OFFSET 分页和基于 `(created_at, id)` 游标的分页；
- 验证比较扫描量、耗时、页间重复/遗漏，以及产品交互成本。

关键追问：`这个优化不仅改变 SQL，还可能改变用户如何翻页。哪些分页能力必须保留？`

## 验证与兜底

每个案例都必须拥有初始、失败和最终三类实验快照。案例校验失败时遵循 [zhixing-case-source-module.md](zhixing-case-source-module.md) 的 `case_invalid`、`environment_unavailable`、`source_insufficient` 分流；环境不可用时可以播放同版本的已验证证据快照，但页面必须显示回放标签。

案例之间不共享用户证据。用户可以从案例一迁移到案例二，但必须开启新的 `PracticeRun`；Tutor 只引用当前案例的事实和来源。

## 一期验收

- 三个案例都能从学习目标进入案例卡，再进入同一训练台；
- 三个案例都支持“用户讨论 -> Tutor 回应 -> 用户尝试 -> 证据校验”的至少两轮循环；
- 任一直接修复建议都不能绕过证据校验；
- 死锁案例能区分止损与根因修复，深分页案例能暴露数据库与产品交互的取舍；
- 慢查询案例可完整生成带来源和证据链的文章预览；
- 模型、知乎搜索或 MySQL 环境不可用时，三案例都能进入相应兜底，不产生伪造成功结论。
