# 知行 MVP 产品需求文档

版本：v0.2

## 1. 产品目标

建立一个桌面优先 Web 形态的个性化技术学习系统。第一版帮助开发者系统学习 Kubernetes：通过初始画像、动态诊断和知乎内容检索，生成并执行一份可调整的四周学习计划。对本地终端和集群上下文，用户可以手动粘贴，也可以通过主动授权的 CLI 连接器自动抓取。

## 2. 用户与使用场景

### 主要用户

有业务开发经验，计划系统学习一项技术但不确定起点、路径和投入方式的开发者。MVP 的技术领域限定为 Kubernetes。

### 典型目标

“我想在四周内系统掌握 Kubernetes，能够理解核心机制、完成基础服务部署，并处理常见部署问题；但我不知道自己缺哪些基础，也不知道每天应该学什么。”

### 衍生场景

- 用户在学习中遇到真实部署任务，系统将任务映射到当前计划中的概念和实践单元；
- 用户准备转型或面试，系统在不丢失主计划的前提下调整时间比例和练习类型；
- 用户有知乎收藏和简历材料，系统将其作为诊断起点并要求用户确认。

这些场景不作为 MVP 主入口，但数据模型和界面需要预留承载位置。

## 3. MVP 主流程

### 流程 A：建立学习画像

用户选择“系统学习一项技术”，填写想学的技术、目标、期望完成时间和每周可投入时间。

用户可选地授权或提供：知乎收藏历史、简历文件、已有项目说明。系统提取候选结论，例如“有 Java 后端背景”“关注过云原生内容”，并要求用户确认、修改或删除。

### 流程 B：动态诊断

系统根据目标和初始材料提出少量问题，而不是一次性发放长问卷。问题覆盖：

- 已有经验和实际使用场景；
- 概念理解和代码/配置阅读能力；
- 学习时间、目标深度和偏好；
- 是否存在近期任务、面试或转型节点。

诊断可以穿插短题和自评，但短题结果优先于自我评级。

### 流程 C：生成并确认学习计划

系统生成默认四周计划，明确展示：

- 最终能力目标；
- 每周里程碑和完成定义；
- 每个里程碑的学习单元、预计时间和实践产出；
- 已依据哪些画像信息做出调整；
- 哪些推断不确定，需要用户确认。

用户可以调整完成日期、可投入时间、偏好和跳过的已掌握内容。调整后系统局部重排计划，不重置已完成记录。

### 流程 D：执行每日学习单元

用户从“今天学什么”进入一个学习单元。单元按以下顺序组织：

1. 本单元目标和它属于哪个里程碑；
2. 必要概念与知乎来源；
3. 原理解释、案例或对比观点；
4. 主动练习，例如预测、解释、配置阅读或修改；
5. 结果反馈和掌握状态；
6. 下一步和预计用时。

### 流程 E：复盘与调整

系统在单元完成、里程碑结束和每周结束时汇总：完成进度、实际用时、薄弱概念、提示依赖和练习结果。

若用户落后、掌握不足或出现真实任务，系统提出带理由的局部调整：补充前置内容、降低/提高难度、拆分单元或插入任务分支。

### 流程 F：K8s 实践闭环

在第三或第四周提供一个部署与排障实践单元。用户阅读或修改 YAML、观察模拟或受控环境中的资源状态，并完成一次诊断和修复。该实践结果回写到相关概念的掌握状态。

| F-03 | 画像确认 | P0 | 系统推断必须逐项展示并允许修改、删除、确认 |
| F-04 | 动态诊断 | P0 | 能根据前序回答改变后续问题，至少包含知识题和时间约束 |

## 5. MVP 学习内容结构

Kubernetes 默认计划为四个里程碑，每个里程碑包含 3 至 5 个学习单元：

| 里程碑 | 能力目标 | 典型产出 |
| --- | --- | --- |
| 1. 建立集群心智模型 | 说明控制面、Node、Pod 和声明式期望状态的关系 | 概念图和解释题 |
| 2. 部署应用 | 理解工作负载、Service、配置和基础网络 | 可阅读并修改的最小 YAML |
| 3. 稳定运行 | 理解资源、发布、健康检查和可观测性基础 | 配置审查和场景题 |
| 4. 排障与迁移 | 依据状态和证据定位常见异常 | 部署/排障综合练习和复盘 |

知乎内容按“原理、经验、案例、对比、练习素材”分类进入单元，不能只按搜索排序直接展示。

## 6. 数据对象

- **LearnerProfile**：已确认的背景、目标、时间约束、偏好和画像证据。
- **LearningPlan**：一项技术的学习计划，包含目标、总时长、里程碑和当前状态。
- **Milestone**：可验证的阶段能力目标和完成定义。
- **LearningUnit**：一次可在 15 至 60 分钟内完成的学习与练习单元。
- **ConceptState**：概念掌握、证据、提示依赖和最后复习时间。
- **Source**：知乎回答或其他可引用内容，以及其在单元中的用途。
- **Checkpoint**：预测、解释、配置修改、案例判断或迁移练习。
- **PlanAdjustment**：一次计划调整的触发原因、影响范围和用户确认结果。
- **TaskBranch**：真实任务、报错或面试冲刺产生的临时分支。

## 7. 桌面优先 Web 核心视图

- **学习总览**：当前长期目标、所在里程碑、今天的学习单元、近期进度和待复习内容。
- **建立计划**：材料输入、画像确认、动态追问和计划预览组成连续流程。
- **计划地图**：四周里程碑、单元、预计时间、完成状态和调整原因。
- **学习单元**：目标、知乎内容、解释、练习、反馈和下一步的沉浸式阅读与实践空间。
- **上下文接入**：手动粘贴 YAML、终端输出或错误日志，或通过本地 CLI 连接器自动抓取；两者均回写实践记录。
- **学习档案**：用户背景、能力推断、来源材料、掌握状态和可编辑偏好。
- **周复盘**：计划与实际差异、薄弱点、迁移表现和下周调整建议。
- **任务分支**：P1，展示真实问题如何关联到主计划并在完成后回归。

Web 页面不直接执行本地命令或读取 `kubeconfig`。CLI 连接器必须由用户主动安装和授权，采集范围限定为当前学习任务；原生桌面打包不属于 MVP，后续可用 Tauri 包装同一套 Web 前端。

## 8. 非功能要求

- 知乎收藏、简历和其他个人材料均须取得用户明确授权，并支持删除与重新分析；
- 不把个人材料中的推断呈现为事实，必须提供用户确认；
- 内容和练习按需加载，计划首屏不一次性请求所有来源正文；
- 每个模型建议说明它使用的学习证据和不确定性；
- 知乎检索失败时，计划和用户已有记录仍可访问，并明确标记缺少来源；
- 前端覆盖首次使用、材料解析中、诊断中、计划生成中、空计划、计划调整、学习完成、来源不可用和权限拒绝状态。

## 9. MVP 指标

- 首次完成学习画像和诊断的比例；
- 用户确认或修改画像推断的比例；
- 计划生成后被保留而非立即重建的比例；
- 每周里程碑完成率和实际/预计时间偏差；
- 学习单元练习完成率和迁移题成功率；
- 周复盘后用户接受局部调整的比例；
- K8s 综合实践中独立完成关键步骤的比例。

## 10. 主要风险

- 需要确认知乎 API 是否提供经授权的收藏历史读取能力；若不提供，不能假设该信号可用；
- 简历解析和历史收藏可能造成错误能力推断，必须以用户确认和动态诊断修正；
- 四周计划过于静态会退化为普通课程表，调整逻辑必须以学习行为和检查点为依据；
- K8s 内容广且版本变化快，来源筛选、时效标记和实践环境必须受控；
- 任务分支、岗位转型和面试模式是扩展路径，不能挤占系统学习主链路的实现资源。
