# 知行 · 知乎黑客松方案（v1.1）

## 0. 摘要

**产品名称**：知行（Knowing-Doing）—— 面向软件工程师的实践健身房。

**一句话定位**：把「我想学一项技术」变成「我要解决一个真实的工程问题，动手解决，再把过程写成文章发布到知乎」。

**核心价值**：AI 时代知识获取变得容易，但实践缺失。知行把大模型从「答案提供者」变成「实践教练」，让用户亲手解决工程问题，并把他们解决问题的过程转化为知乎上的原创内容——从「在知乎学」到「在知乎写」。

---

## 1. 背景与痛点（为什么现在做）

### 1.1 知识获取的「悖论」

AI 让获取任何知识都变得无比方便：输入问题，立刻得到答案。这带来一个悖论——**知识越唾手可得，真实的实践能力越稀缺。**

- 看 AI 给的解释，感觉学会了；
- 遇到生产问题，还是不会处理；
- 让 AI 直接生成代码，代码「看起来能跑」，但自己不会调错。

**「看得懂」和「做得出来」之间的鸿沟**，对软件工程师尤其致命：

1. **工程能力是实践驱动的**：真正的工程能力来自「在真实环境里犯错误并纠正」的经历；
2. **AI 恰恰抹除了这种经历**：AI 会帮你避开错误，你不会知道「如果错了会怎样」；
3. **长期依赖 AI 会削弱人的判断力**：不是 AI 有错，是「人的练习」没有发生。

这是所有软件工程师的趋势性焦虑，也是当下最大的问题。

### 1.2 知识平台与内容的断层

工程师的学习路径通常是：看书/看博客/看教程 → 眼睛会了；试着动手做 → 卡住；卡住后搜索 → 得到一堆模板答案；放弃，等真正遇到工作需求再说。

**问题在于：**
- 教程缺乏「真实工程上下文」（没有真实业务场景、真实数据量、真实报错）；
- 知识平台（知乎等）的价值是真实经验，但用户不知道该选哪篇，也没有人带着他们用；
- 没有一个产品能把「知」与「行」真正连接起来。

### 1.3 知乎自己的内容问题

知乎作为知识社区，面临类似的问题：

- **AI 生成内容泛滥**：大量内容是无实践验证的；
- **真实创作者稀缺**：真正有经验的开发者，要么忙于工作，要么不知道如何把经验系统化输出；
- **如何让创作者持续产出**：一个工程师从「会做」到「会写」，需要大量的整理工作，这块是知乎现在的瓶颈。

**知行就是知乎「内容生产系统」的补充**：帮工程师从「做完」到「写出来」。

## 2. 产品定位（核心）

### 2.1 一句话

> **知行：软件开发者的实践健身房。**
> 用户带着真实的工程问题来，在 AI 教练的引导下亲手解决，然后自动生成一篇有验证过程的知乎文章。

### 2.2 不是「学习计划」，是「实践教练」

- 传统学习产品：内容 → 用户 ← 答案。用户消费内容，获得答案。
- 知行：**问题 → 实践 → 文章**。用户面对问题，动手实践，产出内容。

### 2.3 产品的三轮闭环

1. **训练**：用户面对一个真实工程问题（用户自己带来的，或平台预置的），在 AI 教练引导下诊断、假设、验证、修复；
2. **记录**：系统自动记录全部实践过程（问题、假设、实验、错误、验证），形成完整的「实践证据链」；
3. **发表**：用户确认后，记录自动整理成**有可复现证据的知乎文章**，一键发布。

---

## 3. 为什么是知乎（产品与平台的互相成就）

### 3.1 知乎为知行提供什么

- **真实经验内容库**：知乎上有大量真实经验分享，可以作为实践的「参考读物」；
- **「继续讨论」入口**：发布后，用户可以在评论区和其他专业人士交流；
- **社区反馈渠道**：发布后能持续获得反馈、讨论，甚至后续合作。

### 3.2 知行为知乎提供什么

- **高质量的原创内容**：每篇文章都有可验证的实践过程和实验数据（AI 生成内容无法替代）；
- **专业创作者**：帮有能力的工程师把经验写出来，成为知乎创作生态的一部分；
- **社区活力**：用户在知乎讨论真实工程问题，答案有实践验证。

**这是一个双赢循环**：知行使知乎的内容更多、更好、更真实；知乎让知行的用户有学习环境、有反馈、有动力。

## 4. 产品功能结构

### 4.1 一次完整的实践（用户视角）

1. **进入**：用户描述自己的问题（如「我们的 Redis 缓存总是不一致」）；
2. **教练引导**：AI 教练提出诊断问题，引导用户自己发现根因；
3. **动手**：用户写代码、改配置、验证（在本地或 CLI 连接器自动化）；
4. **记录**：系统记录整个过程（诊断、假设、尝试、错误、验证数据）；
5. **认证**：每次成功的验证必须打印证据（日志、指标、结果）；
6. **整理**：系统把这些记录整理成文章（可编辑、可调整）；
7. **发布**：用户确认后，发布到知乎，可选择公开或保存草稿。

### 4.2 三种实践模式

| 模式 | 用户 | 问题来源 | 功能 |
| --- | --- | --- | --- |
| **场景模式** | 用户想系统学习某技术 | 平台预置的案例场景 | 学完理论知识，动手实践，形成笔记 |
| **任务模式** | 用户遇到真实问题 | 用户自己的工作问题 | 直接上手，解决后写成文章 |
| **创作模式** | 用户有实践经验 | 用户的经历 | 只记录实践过程，一键成文 |

**本次黑客松只交付场景模式。** 任务模式和创作模式只作为后续路线图，避免三个模式同时开发而没有一个完整闭环。

### 4.3 教练的黄金法则

- 不直接告诉用户答案；
- 用**提问和线索**引导用户想到答案；
- 每次实践后，引导用户总结、记录、确认。

## 6. MVP 范围（黑客松版本）

### 6.1 一个闭环

- **1 个技术领域**：MySQL 慢查询与 EXPLAIN；
- **1 个真实案例**：一个真实的、可验证的工程问题；
- **1 篇文章产出**：从实践的记录，到可编辑文章，到发布（或模拟发布）到知乎。

### 6.2 核心体验

- 用户看到问题描述和症状；
- 用户输入假设 / 方案；
- AI 教练展开追问，引导排查；
- 用户进行实践并验证（提供手动粘贴或 CLI 抓取的上下文）；
- 系统自动记录实践过程；
- 一键整理成文章；
- 用户确认、发布。

### 6.3 已冻结的实现边界

- 教练采用“剧本化状态机 + 提示阶梯”：代码控制阶段、通过条件和提示级别，模型负责当前阶段内的提问与解释；
- 练习环境使用本地 Docker 和固定种子数据，手动粘贴 EXPLAIN / 基准结果是主线；
- 发布以高保真知乎草稿预览为主线，真实 OAuth 发布只在核心闭环全绿后接入；
- 无账号体系、不读取收藏、不开启真实任务模式；
- Kafka 与 Redis 复用同一案例引擎，在 MySQL 闭环稳定后再接入。

## 7. 为什么评委应该给我们第一

知行值得高分，不是因为又加入了一个 AI 对话框，而是因为它把“AI 能回答”转化为“人能证明自己做过”。

1. **对知乎有明确增量。** 知行消费知乎中的真实经验，也把开发者的验证过程整理成可讨论的原创文章。它补的是从实践到创作的生产链，而不是再做一个内容分发页。
2. **核心体验不可被普通问答替代。** 评委看到的是“工程症状 -> 假设 -> EXPLAIN 证据 -> 错误尝试 -> 修复对比 -> 文章”，而不是一段看起来正确的聊天答案。用户必须提交证据，系统才允许结论成立。
3. **技术路线可控而非概念堆砌。** 状态机负责教学边界和演示稳定性，LLM 只负责追问和表达；Docker 与固定种子保证现场可复现；失网时可回放，不依赖模型临场发挥。
4. **MVP 小但完整。** 一个 MySQL 案例已经覆盖知乎内容编排、AI 教练、用户实践、证据链和文章预览。Kafka、Redis、真实任务和 OAuth 是清晰的复用路径，不是为凑功能写的愿望清单。

## 8. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 知乎发布 API 授权门槛 | MVP 优先完成「生成文章→预览→确认」；赛前争取完成真实 OAuth 集成，并在演示当天完成一次真实发布 |
| 产品功能过多，48h 做不完 | MVP 只保留一个完整闭环（1 个领域 + 2-3 个页面 + 1 条闭环），其余作为扩展方向描述 |
| 被评委归类为「又一个 AI 学习助手」 | 全部称呼用「实践」「训练」而非「学习」；提交材料强调「先做后学」而非「先学后做」 |
| 知乎内容质量参差 | 不把「来源来自知乎」当卖点；卖点是「内容与学习路径的匹配」，即「为什么现在读它」 |
| 实践环节需要本地环境 | 提供 Docker 一键启动的练习环境，手动粘贴日志/配置即可，CLI 连接器是增强而非依赖 |
