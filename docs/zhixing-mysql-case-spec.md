# 知行 MySQL 慢查询案例规格

版本：v1.1

## 1. 案例目的

这个案例不是“教用户背索引口诀”，而是训练一条工程判断链：面对慢查询，先看现象，再提出可证伪的假设，用执行计划验证，修改后重新比较证据。

案例 ID：`mysql-order-list-index-001`

模式：平台预置场景模式。

数据状态：本地 Docker 中的固定种子演示数据。任何页面数字都标注为“演示环境”，除非来自用户实际粘贴的运行结果。

## 2. 工程背景

运营后台按用户、订单状态和自然日查询订单列表。高峰期订单列表接口 p99 升高，业务要求保持筛选语义和按创建时间倒序，不能通过删条件或缩小结果集伪造优化。

首次进入只展示以下材料：

- 演示环境的慢查询现象：订单列表接口 p99 升高；
- 业务约束：保留用户、状态、自然日筛选与创建时间倒序，不能删条件或缩小结果集；
- `orders` 表结构与现有索引。

原始慢 SQL 不在入口展示。用户需要主动提出“查看慢日志”，或在 Tutor 追问后选择获取它；系统先展示一段脱敏慢日志，用户需从中选出与订单列表症状相符的语句。用户在尚未选中语句时提出某种怀疑是允许的，但不能直接运行 `EXPLAIN` 或进入修复验证。

MVP 的脱敏慢日志固定只含两条候选语句：目标订单列表 `SELECT` 与一条无关的后台统计语句。两条都保留查询耗时、扫描行数、时间和 SQL 结构，替换用户 ID、订单号、IP 等真实值为占位符。用户选中目标语句后，Lab 才展示固定种子数据对应的可运行副本；该副本保留相同查询形态，但使用安全的演示参数。

用户选中无关语句时，Tutor 只要求用户解释该语句与订单列表 p99 症状之间的因果关联，不直接指出选错。用户应自行对照接口、表、查询形态和耗时判断不匹配。连续两次选中无关语句后，才定向引导用户检查与 `orders`、订单列表筛选和高耗时相对应的 `SELECT`。该 `log_selection_mismatch_count` 是日志定位环节的专用计数，不与全局“连续三次无有效进展”的提示计数相加。

用户选中目标语句并获得可运行演示副本后，Tutor 主动说明当前仍缺少验证证据，并只围绕“下一步如何验证”发起一个开放式追问。工作台将该 SQL 作为带来源标识的只读参考展示，另提供空白执行编辑器。Tutor 不自动运行 SQL、不自动提交假设，也不默认写入完整的 `EXPLAIN` 语句；只有用户索取示例或触发提示阈值时，才可提供最小命令模板，且用户必须确认执行。

原始慢 SQL（从慢日志获得后的案例材料）：

```sql
SELECT id, user_id, status, total_amount, created_at
FROM orders
WHERE user_id = 4242
  AND status = 'PAID'
  AND DATE(created_at) = '2026-08-01'
ORDER BY created_at DESC
LIMIT 20;
```

建议表结构：

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  status VARCHAR(20) NOT NULL,
  created_at DATETIME NOT NULL,
  total_amount DECIMAL(12, 2) NOT NULL,
  KEY idx_orders_user_id (user_id)
);
```

## 3. 场景状态机

| 阶段 | 用户任务 | 必需证据 | 不允许的跳过方式 | 通过条件 |
| --- | --- | --- | --- | --- |
| `observe` | 阅读症状和表结构，说明下一个要获取的事实 | 对慢点的初始判断、索取慢日志并选中目标语句的动作 | 直接声明“建联合索引” | 能说明仅凭索引定义无法判断实际访问路径，并选中与场景匹配的慢 SQL |
| `hypothesize` | 阅读选中的可运行 SQL，提出至少一个可验证假设 | 假设文本与验证命令 | 把 AI 结论当证据 | 假设能被 EXPLAIN 证伪或支持 |
| `inspect` | 对原始 SQL 执行 EXPLAIN，并解释观察 | 原始 EXPLAIN、解析出的字段、用户观察 | 只贴一句“没走索引” | 识别并解释 `type`、`key`、`rows` 和 `Extra` 中至少两项 |
| `attempt` | 提交一次 SQL 或索引修改并解释预期 | 修改 SQL 或索引、第二份 EXPLAIN | 修改结果集语义 | 若证据不足，能说明当前改动的局限；若证据充分，可直接进入验证 |
| `verify` | 改写时间条件并评估联合索引 | 修改 SQL、最终 EXPLAIN、基准对比 | 只提交“优化完成” | 结果语义一致，扫描成本下降，结论与证据对应 |
| `resolved` | 查看已验证的解决结果与笔记生成状态 | 支撑根因与修复的证据链接、残余风险 | 只因提出方案就标记完成 | 实践闭环完成；笔记不自动跳转，可结束训练 |
| `reflect` | 编辑自动生成的判断路径和残余风险 | 最终结论、复现步骤 | 只复制模型总结 | 编辑笔记、按需生成完整文章初稿 |

## 4. 提示阶梯

下表定义每一级提示应引导出的判断或动作，不固定具体措辞。Tutor 依据用户当前输入生成语言，但不能越过下表的提示强度。

| 阶段 | 提示 1 的引导目标 | 提示 2 的引导目标 | 提示 3 的引导目标 |
| --- | --- | --- | --- |
| `observe` | 引导用户区分“慢”与“未走索引”，识别缺失事实。 | 引导用户从脱敏慢日志定位触发症状的 SQL。 | 引导用户对选中 SQL 执行 EXPLAIN，并记录核心字段。 |
| `inspect` | 引导用户检查谓词是否对列做了计算。 | 引导用户判断时间条件是否仍可使用 B+ 树范围定位。 | 引导用户将日期条件改为左闭右开范围，并再次比较计划。 |
| `attempt` | 引导用户比较单列索引和多条件过滤的关系。 | 引导用户理解等值列、范围列与联合索引列序的关系。 | 引导用户比较候选联合索引与现有单列索引对查询的覆盖程度。 |
| `verify` | 引导用户避免单独以 `type` 判断成败。 | 引导用户同时比对计划、耗时和结果集一致性。 | 引导用户按成本、语义和代价判断，不将某一执行计划字段视作唯一标准。 |

初始 `EXPLAIN` 返回后，工作台立即保存并展示完整原文与可见的结构化字段。Tutor 的第一轮响应只引导用户自行提出观察或不确定点；在用户作出观察前，不解释执行计划、不给出索引结论，也不推动到修改阶段。

## 5. 推荐修复

SQL 改写：

```sql
SELECT id, user_id, status, total_amount, created_at
FROM orders
WHERE user_id = 4242
  AND status = 'PAID'
  AND created_at >= '2026-08-01 00:00:00'
  AND created_at < '2026-08-02 00:00:00'
ORDER BY created_at DESC
LIMIT 20;
```

待验证的候选索引：

```sql
CREATE INDEX idx_orders_user_status_created
  ON orders (user_id, status, created_at);
```

该索引是案例中的候选方案，不是脱离数据分布、写入成本和查询形态的通用处方。案例需要让用户说明：为什么等值过滤列在前，时间范围列在后；以及新增索引的写放大与空间成本。

### 预置不充分尝试

案例为 Demo 回放和 Tutor 兜底预置一种不充分尝试：创建候选联合索引，但保留原始 `DATE(created_at)` 条件。它不预设为“完全没有使用索引”：在固定种子下，优化器可能利用联合索引的等值前缀或排序顺序；但时间列不能作为有效范围条件，扫描成本仍可能不满足本案例的验证标准。

用户不必走该路径：可以先改写时间条件、直接提出完整方案、做其他可执行修改，或索取帮助。Tutor 根据用户意图、实验结果和当前缺失证据动态追问或给出参考卡，不预设下一句追问和唯一操作顺序。任意尝试是否充分都由 Lab 固定种子下的实际结果、语义校验和验证规则判断。

## 6. 证据卡契约

| 类型 | 保存原文 | 最小结构化字段 | 页面用途 |
| --- | --- | --- | --- |
| 症状 | 是 | p95/p99、发生时间、环境标签 | 起始问题 |
| 慢日志 | 是 | 脱敏规则、候选语句、用户选中语句 ID | 定位问题 SQL |
| SQL | 是 | 语句版本、语义约束 | 对比与文章 |
| EXPLAIN | 是 | `type`、`key`、`rows`、`Extra` | 假设验证 |
| 修改 | 是 | SQL / DDL、操作者说明 | 失败尝试与最终修复 |
| 基准 | 是 | 耗时、样本数、运行环境 | 前后对比 |
| 结论 | 是 | 支持证据 ID、残余风险 | 文章与复盘 |

前后对比只在相同种子、相同环境、相同查询语义下成立。环境不同或样本不足时，系统应标记为“倾向支持”，不能宣称“性能提升 X 倍”。

## 6.1 自动笔记大纲

实践进入 `resolved` 后，系统自动生成可编辑的工程复盘大纲，包含：问题与约束、采取过的判断、执行与证据、失败尝试、最终方案与残余风险。大纲段落必须保留对应的事件 ID、证据 ID 或来源 ID；缺失素材显示待补，不编造内容。用户从笔记页主动发起后，系统生成完整、可编辑且待人工审核的文章初稿；正文相关段落提供轻量证据或来源入口，文末汇总完整来源列表；不自动发布。

## 7. 知乎来源使用方式

工作台中的知乎参考卡使用“面向当前问题的改写导引 + 明确来源”模式：Tutor 可以将已核验来源改写成简短的原理说明、排查角度或权衡提醒，使其贴合用户当前的证据和疑问；卡片必须显示“基于来源改写”、标题、作者、原文链接和当前使用理由。用户可展开查看允许展示的原始摘录，或打开原文；改写内容不能伪装成用户实验结果或客观性能结论。

每条来源只承担一个明确角色：

- `principle`：解释 EXPLAIN、优化器成本或索引范围；
- `case`：提供类似 SQL 与排查路径；
- `tradeoff`：说明索引可用不等于应使用，以及写成本与数据分布；
- `practice`：提供可以复现的命令或实验方向。

来源展示必须包含标题、作者、链接、引用片段和“为什么当前读它”。不以赞同数替代事实验证，也不把搜索摘要直接写入用户文章。

每张改写参考卡只回答一个当前判断问题，并记录 `source_id`、改写版本、所支持的断言和对应案例阶段。改写前必须确认原文或允许使用的摘录确实支持该断言；无法确认时只显示原文入口，不生成解释性改写。实验中的 `rows`、耗时、结果集或“修复成功”结论始终只由 Docker Lab 证据支撑。

## 8. 演示关键帧

1. 展示症状、表结构和现有索引，不展示原始 SQL；
2. 用户请求查看慢日志，系统展示一段脱敏慢日志；
3. 用户选中订单列表对应语句，系统提供等价的可运行演示副本；
4. 用户提出一个关于索引利用的可验证假设，教练引导其说明验证方式；
5. 执行初始 EXPLAIN，形成第一张证据卡；
6. 用户做一次不充分的修复，系统记录“失败尝试”；
7. 修改时间范围与联合索引后，展示前后证据对比，并标记问题已解决；
8. 系统自动生成可编辑笔记大纲；用户按需点击“整理成文章”，显示有证据来源和残余风险的草稿预览。
