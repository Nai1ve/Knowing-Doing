# 知行阶段化交付方案

版本：v1.1

## 1. 交付目标与范围

知行的长期方向是开发者的实践学习系统：把系统学习、真实任务、实践证据和原创表达连接起来。

黑客松 MVP 不试图一次实现这个全景。当前必须完成的是三个共享引擎的 MySQL 案例闭环：

```text
MySQL 工程案例
  -> 用户讨论判断或下一步动作
  -> Tutor 基于事实回应并追问
  -> 用户在受控 Docker Lab 的 SQL 窗口中执行尝试
  -> 系统记录原始证据并校验
  -> 用户基于结果进入下一轮讨论
  -> 生成可编辑的知乎文章预览
```

本轮只支持平台预置的 **场景模式**，并准备慢查询与联合索引、死锁与锁等待、深分页优化三个 MySQL 案例。慢查询是三分钟主 Demo；任务模式、创作模式、Kafka、Redis、真实 OAuth 发布和自动 CLI 抓取不进入首个闭环的关键路径。

## 2. 实现原则

1. **先完成可演示纵切，再扩展技术面。** MySQL 从进入案例到文章预览全程可走通，才接 Kafka 或 Redis。
2. **代码持有流程，模型持有表达。** 场景状态、通过条件、提示级别和事件结构是确定性代码；模型只生成当前阶段的追问、解释和文章草稿。
3. **原始证据优先。** SQL、EXPLAIN、日志和基准结果以原文保存；模型结论必须链接到这些证据。
4. **每阶段可独立验收。** 阶段完成后先审核成果、风险和下一阶段输入，再继续开发。
5. **演示不依赖脆弱外部服务。** Docker、固定种子数据和回放模式是主线；模型和 OAuth 故障不能阻断演示。
6. **前端按需取数。** 总览只取案例摘要；打开训练台再取当前阶段、来源摘要和事件；原始证据和文章素材分页或按操作加载。

## 3. 阶段总览

| 阶段 | 目标 | 可见成果 | 完成后不再改变的决定 |
| --- | --- | --- | --- |
| 0. 冻结 | 冻结 MVP、Demo 和案例规格 | 三案例包、主 Demo 脚本、验收表 | 三个 MySQL 案例、场景模式、模拟发布 |
| 1. Docker Lab 与证据 | 先建立可复现的 MySQL 实验和验证数据 | Docker、种子数据、慢日志、前后 EXPLAIN/基准 | 环境契约、证据格式和通过阈值 |
| 2. 讨论与记录 | 将工作台、状态机、Tutor 与原始证据接成动态训练闭环 | SQL 执行区、事件时间线、提示阶梯、固定参考 | 状态判定与模型权限边界 |
| 3. 写作 | 从已记录证据自动形成笔记并生成文章初稿 | 可编辑笔记、完整文章初稿、来源与模拟发布 | 人工审核和发布前检查边界 |
| 4. 演示加固 | 可在失网或模型异常时稳定演示 | 回放、重置、彩排和备份视频 | 代码冻结点 |
| 5. 扩展 | 复用案例引擎增加 Kafka、Redis 和真实连接 | 新案例与集成能力 | 不影响 MySQL 核心行为 |

## 5. 阶段 1：Docker Lab 与证据基线

### 要做

- 使用平台预先提供且长期运行的单个 MySQL 8 Docker；应用不创建、销毁或启动容器，不暴露数据库端口。人工执行编号 migration，创建三个案例 schema、表、固定种子和基线索引。
- 通过 Lab API 提供健康检查、案例级 FIFO、命名会话、受控 SQL 执行和一键重置；账号密码不进入任何记录，运行期不执行建表 DDL。
- 生成并保存脱敏慢日志、目标 SQL 的安全演示副本，以及初始、预置不充分尝试、最终修复三类实验快照。
- 定义 EXPLAIN、基准和结果集校验的原始输出格式及解析字段：`type`、`key`、`key_len`、`rows`、`Extra`、耗时和环境标签。
- 将“修复成功”定义为相对判断：结果集保持语义一致，扫描成本和基准满足阈值；不把某个具体 `type` 值写成唯一成功标准。

### 验收

- 在平台指定的 MySQL 8 上，执行人工 migration 后可以复现三个 MySQL 案例、执行各自的预置尝试并回到一致初始状态；应用启动不创建 Docker 容器。
- 每份快照都保留原始输出、环境标签和可追溯的生成脚本；不连接真实业务库，不读取用户数据库凭据。
- 问题路径、预置不充分尝试和候选修复都能产生不同的可见证据；尚未达到阈值时不会伪造“已解决”。

## 6. 阶段 2：讨论与记录

### 要做

- 将现有 K8s Mock 替换为通用 `EngineeringScenario`、`EngineeringCase`、`CaseStage`、`PracticeEvent` 和 `EvidenceArtifact` 类型。
- 实现受控 SQL 工作台：只读 SQL 参考、空白执行区、执行确认、原始输出、证据卡与重置入口；工作台只连接阶段 1 交付的 Docker Lab。
- 实现状态机与事件追加：用户可从任意可执行操作开始；只有证据条件可推进到 `resolved`，不从聊天文本反推完成。
- 接入 Tutor：以当前输入、已有证据和缺失条件为输入，动态生成追问、提示或按需参考卡；它不得自行执行 SQL、伪造证据或硬编码用户路径。
- 接入已核验的知乎参考卡、脱敏外部粘贴和来源边界；所有用户输入、SQL、输出、提示和引用进入同一记录链。
- 保持 API service / Pinia 按领域拆分，训练台按需请求当前案例、阶段、证据和参考，禁止单页集中预取全部数据。

### 验收

- 不接 LLM 时，使用 Docker Lab 或同版本预置证据仍可从案例进入 `resolved`；Tutor 异常只降级为预置引导，不改变状态判定。
- 用户可以走不同讨论和操作路径；直接方案、错误尝试与外部粘贴都被记录，但只有 Docker Lab 原始输出可作为验证证据。
- 每个状态变化、Tutor 响应和参考卡都可追溯到事件、证据或来源；刷新后恢复当前实践记录。
- 前端生产构建通过，且页面不再展示 Kubernetes 案例内容。

## 9. 阶段 5：案例与能力扩展

### Kafka

复用“症状 -> 分区级证据 -> 假设 -> 验证 -> 复盘”模型。首个案例是单分区热点或 Rebalance，证据为 partition Lag、消费耗时和消费者日志；不能把“增加消费者”写成默认答案。

### Redis

复用“约束 -> 时序证据 -> 方案选择 -> 失败注入 -> 残余风险”模型。首个案例是缓存回填旧值；重点是业务可接受的不一致窗口，不把延迟双删当成绝对答案。

### 真实集成

按顺序接入 CLI 自动抓取、知乎 OAuth 发布、真实任务模式和长期学习计划。每项外部连接都先定义授权范围、失败态、撤销方式和审计记录。

## 10. 阶段评审模板

每阶段结束后固定回答以下问题，再进入下一阶段：

1. 本阶段的用户可见能力是否按验收标准完成？
2. 新增的原始证据、模型推断和来源引用是否被清楚区分？
3. 是否引入了对外部服务或不可复现环境的关键依赖？
4. 当前最可能使 Demo 失败的三个风险是什么？
5. 下一阶段是否真的需要开始，还是应先修复当前闭环？
