# 知行产品方向

版本：v0.2（黑客松 MVP 产品定稿基线）

## 一句话定位

知行是一个面向程序员的 AI 个性化学习规划与执行系统：它先理解一个人想系统掌握什么技术、已有何种基础和可投入多少时间，再利用知乎优质内容生成、执行并持续调整数周学习计划。

## 核心问题

程序员面对一项新技术时，通常同时遇到三类困难：

- 内容分散，不知道应该从哪里开始、按什么顺序学习；
- 自我判断不准确，不知道哪些已经掌握、哪些只是看懂了；
- 真实任务、岗位变化或面试压力会打断原计划，却没有机制将它们转化为学习路径的一部分。

AI 能快速给出答案，但不能天然决定“对这个人而言，此刻应该学什么”。知行要解决的是学习规划和学习执行的连续性，而不是增加一个泛化问答入口。

## 产品主线

系统学习一项技术是第一优先级。用户以“我想系统学习 Kubernetes”“我想补齐 Redis 能力”等目标进入，获得带里程碑、进度和动态调整机制的数周计划。

其他需求是主线的分支：

| 用户诉求 | 在知行中的位置 | 对计划的影响 |
| --- | --- | --- |
| 当前工作任务或线上问题 | 任务分支 | 插入最小必要学习单元，完成后回归主计划 |
| 岗位转型 | 目标设定分支 | 调整目标能力模型、时间和项目实践比例 |
| 面试准备 | 阶段冲刺分支 | 压缩理论路径，增加表达、案例和模拟题 |
| 收藏内容积累 | 画像与内容信号 | 作为已有兴趣和基础的初始证据，不直接等同于掌握 |

## 个性化模型

个性化不依赖单一的“初级/中级”标签，而由四类信号共同形成：

1. **初始材料**：用户主动描述的目标、知乎收藏历史、简历文件或手工选择的经历。
2. **动态追问**：系统针对目标、实际经验、可投入时间和偏好提出少量澄清问题。
3. **学习行为**：阅读、作答、提示依赖、练习完成和复习间隔。
4. **迁移表现**：用户能否在新题目或真实任务中使用所学概念。

系统必须将推断展示给用户确认和修改。收藏、简历和模型判断只能是画像假设，不能作为事实直接写入学习计划。

## 学习闭环

```text
目标与材料
  -> 学习画像与动态诊断
  -> 数周学习计划与里程碑
  -> 每日学习单元：理解、练习、应用
  -> 检查点与学习记录
  -> 周复盘与计划调整
  -> 真实任务/面试等分支处理后回归计划
```

每个学习单元应包含：当前目标、必要概念、外部实践工具入口、知乎来源、AI 对话、主动练习、结果反馈和下一步。用户可以将常用判断、AI 回答或知乎摘要固定到当前工作台。系统不能只给出内容清单，也不把编辑器或终端伪装成嵌入式组件。

学习笔记不是一个空白文本框，而是一条“实践到文章”的记录链：系统默认记录参考内容、用户提出的问题、Tutor Agent 对话、终端错误、运行观察和用户留下的证据；AI 基于这些带来源的素材生成文章大纲；用户确认和调整大纲后，再选择由模型完成文章或自行写作；最后进入知乎发布前的人工检查和授权发布流程。原始素材、大纲和文章正文必须分层保存，避免模型改写后丢失事实依据。

## 首个 MVP 技术领域

Kubernetes 系统学习。

首期用户是具有业务开发基础、想在四周内建立 Kubernetes 可部署、可解释、可排障能力的后端或全栈开发者。K8s 部署和故障排查是计划中的实践单元，用来验证学习是否能够迁移到真实场景，而不是产品的总入口。

默认四周计划可包括：

1. 集群心智模型与基础对象；
2. 工作负载、服务发现和配置；
3. 发布、资源、可观测性与安全边界；
4. 部署实践、常见故障诊断和综合复盘。

该结构是可编辑的默认方案，系统会根据基础、目标和可投入时间增删或调整节奏。

## 知乎的产品价值

知乎不是计划末尾的参考链接库，而是内容编排和学习解释层：

- 从检索结果中提取原理解释、真实经验、对比观点、失败案例和实践建议；
- 将内容关联到计划中的概念、里程碑和练习，而不是按热度堆叠；
- 在学习单元和任务分支中提供可追溯来源；
- 根据用户的收藏、阅读和当前错误形成更准确的检索意图。
- 在当前学习工作台中，以当前问题为检索上下文展示摘要、来源作用和继续查看入口。
- 将实践中的参考、问题、错误和观察自动沉淀为可追溯素材，支持从素材到大纲、从大纲到文章的连续整理。

### 学习工作台的边界

当前学习页是执行一次学习任务的工作台，不是数据仪表盘，也不是 IDE 或终端替代品。它负责把目标、外部工具、AI 追问、知乎知识和学习证据连接起来：

- 编辑器、终端和运行数据在用户本地或既有工具中打开；
- 知行提供当前节点、任务上下文和下一步动作；
- 知行 AI 通过追问帮助用户解释现象，不直接替代用户完成判断；
- 知乎内容以当前问题相关的摘要和可追溯来源进入工作台；
- 用户完成实践后，把结果和证据带回知行，更新计划与掌握状态。
- 工作台动作、Tutor Agent 对话和学习证据自动进入“实践记录”；用户在独立的学习笔记模块中完成大纲确认、文章编辑和知乎发布。
- 上下文接入提供两条等价路径：用户可以手动粘贴 YAML、终端输出或错误日志，也可以主动授权本地 CLI 自动抓取；两者进入同一条实践记录流。
- MVP 采用桌面优先 Web 形态，不直接打包原生客户端。需要访问本地终端、文件或 Kubernetes 上下文时，通过独立的本地连接器承接权限和采集，不让 Web 页面直接执行任意命令。

### 实践到文章的 MVP 边界

- **自动记录**：记录事件类型、原始内容、来源、发生时间和关联学习单元；错误和失败尝试与成功结果同等重要。
- **AI 整理大纲**：模型只能基于已记录素材生成候选结构，必须保留依据来源，不能把推测写成已验证事实。
- **人工确认**：用户可以删改、调序、补充观点，并决定哪些内容适合公开发布。
- **成文与发布**：模型完成文章只是草稿能力；知乎发布前需再次检查来源、隐私、敏感信息和引用，并由用户确认授权。

### 上下文接入边界

- **手动粘贴**：适用于无需安装工具、远程集群或用户只愿意分享部分信息的场景；用户明确选择要提交的内容。
- **CLI 自动抓取**：适用于本地开发和 K8s 排障；用户安装并主动授权连接器，连接器只采集当前任务需要的命令输出、配置和错误上下文。
- **统一记录**：两条路径都生成同样的素材事件，包含类型、原始内容、来源、时间和关联学习单元，后续由 Tutor Agent 分析并进入文章工作流。

具体 API 字段、收藏历史权限、引用要求和限流仍需在实现前核验。未能获取收藏历史时，系统使用用户描述、简历和诊断问答完成冷启动。

## MVP 成功标准

对“系统学习 Kubernetes”的用户，知行应能：

- 在首次会话中生成一份用户可理解、可编辑的四周学习计划；
- 根据用户的诊断结果和时间预算调整里程碑和学习单元；
- 在每个学习单元中组织知乎来源、原理、练习和反馈；
- 可视化记录学习进度、薄弱概念和下一步；
- 在一次 K8s 部署或故障排查实践中验证至少一个概念的迁移；
- 在周复盘后给出有依据的计划调整，而不是重新生成整套课程。

## 明确不做

- 不做覆盖全部技术栈的课程市场或内容社区；
- 不承诺只凭简历或收藏就准确评估技术能力；
- 不把所有用户强行导向相同的 K8s 路线；
- 不在 MVP 阶段实现生产集群的全功能运维控制台；
- 不用大段 AI 总结替代来源、练习和学习记录。

## 产品原则

1. **诊断先于推荐**：先理解目标与基础，再安排内容和难度。
2. **里程碑先于内容堆积**：用户始终知道本周目标、当前进度和下一步。
3. **计划可调整但不可失忆**：每次调整都显示原因、影响范围和保留内容。
