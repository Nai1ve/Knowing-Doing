# 知行 Post-MVP 能力扩展方案

## 1. 目标与主线

MVP 已经证明了“进入工程案例 -> 实践 -> Tutor -> 证据 -> 写作沉淀”的闭环。Post-MVP 不先扩充大量案例，而是把这条局部闭环接回完整的学习过程，让知行真正回答三个问题：

1. 用户为什么要学习这项技术，以及系统如何判断起点；
2. 用户接下来应该学习什么，以及路线为什么这样安排；
3. 用户完成一次实践后，计划如何根据真实证据发生变化。

产品主链固定为：

```text
目标与画像 -> 学习计划 -> 当前学习活动 -> 实践与 Tutor
-> 证据与掌握判断 -> 用户确认的计划调整 -> 写作沉淀 -> 知乎发布
```

MySQL Lab、Tutor、实践记录和自动写作继续复用。新增通用 `LearningActivity` 作为所有学习单元的活动容器；MySQL `PracticeRun` 是其中一种 Lab 执行能力，不再承担所有技术领域的学习状态。

## 2. 能力地图

| 优先级 | 能力 | 交付结果 |
| --- | --- | --- |
| P0 | 真实学习主线 | 用户输入目标后看到真实计划，进入当前单元；实践完成后计划状态同步更新 |
| P1 | 诊断与学习画像 | 目标、时间、经验、简历和诊断回答形成可确认、可修改的画像依据 |
| P1 | 可解释的计划引擎 | 生成数周路线、里程碑、当前节点、依赖关系和安排理由 |
| P1 | 掌握判断与计划调整 | 从实践证据提炼能力变化，提出调整草案，用户确认后更新未开始单元 |
| P2 | 外部实践与知乎来源 | 通过上下文回传完成非 Lab 实践，并按当前学习节点编排知乎来源 |
| P2 | 通用案例框架 | 用 Kafka 消费延迟验证事件、Tutor、来源、证据和写作不依赖 SQL |
| P3 | 知乎 OAuth 与发布 | 绑定当前 learnerId，写入文章草稿并在用户确认后发布 |
| P3 | 多计划与真实任务分支 | 管理多份计划，允许临时工程问题从主计划分出并回归 |
| P3 | 跨设备与运营能力 | OAuth 身份、跨设备同步、隐私管理、任务监控和模型调用观测 |

## 3. 第一阶段：统一真实计划主线

这是下一阶段的首个开发里程碑。目标不是重做 MySQL Lab，而是移除计划和实践之间的断层。

### 后端

- 统一使用现有 `Intake -> ProductPlan -> PlanUnit` 作为计划数据源；增加计划概览、当前单元和单元摘要读取接口。
- 扩展 `PlanUnit`，增加单元类型 `orient / learn / practice / checkpoint / synthesis`，实践方式 `lab / external / guided`，以及目标、预计投入、依赖、来源摘要和安排理由。
- 新增 `LearningActivity`，记录 learner、plan unit、活动方式、目标快照、状态、当前步骤、事件、证据和 revision。
- 现有 MySQL `PracticeRun` 通过 `activity_id` 关联到 `LearningActivity`。已有实践回填活动记录，原有 run、Tutor、Lab、Pin 和文章接口保持兼容。
- Lab 单元启动活动后再申请 Lab；external 单元不申请容器，通过上下文回传完成实践。
- 实践进入 `resolved` 后只完成关联单元并生成计划调整建议，不直接重排用户路线。

### 前端

- `/overview` 改为默认入口，移除总览、路线、侧栏对旧 Mock `LearningPlan` 的依赖。
- 总览只展示目标、当前计划、当前里程碑、当前单元和下一步动作；完整路线单独进入 `/route`。
- 计划单元根据 `practiceMode` 进入 MySQL Lab、外部实践或引导阅读，不把所有单元都渲染成 SQL 工作台。
- 完成实践后显示“单元已完成”和“计划调整待确认”，用户可以进入调整详情，而不是自动跳转或静默修改路线。

### 第一阶段完成标准

用户可以完成以下路径：

```text
输入学习目标 -> 创建真实计划 -> 进入当前 MySQL 单元
-> 完成实践 -> 返回计划 -> 看到单元完成与下一步
```

## 4. 第二阶段：画像、诊断与 Planner

### 画像输入

- Intake 收集目标技术、目标能力、每周可投入时间、已有经验自评和预期产出。
- 支持上传 PDF 简历；使用成熟 PDF 文本提取库，不自研格式解析器。
- PDF 只在请求期间临时保存。提取完成后删除原文件，数据库仅保存解析文本投影、候选能力和用户确认结果，不保存原 PDF。
- 用户可以编辑、删除或拒绝每一条画像依据。模型推断必须显示为候选信息，不能直接成为最终画像。

### 诊断与计划

- 新增 `ProfileEvidence` 和 `DiagnosticTurn`，记录来源、内容、用户确认状态和关联目标。
- 诊断 Agent 根据目标和画像不确定性提出 1 至 3 个高价值问题；不进行无意义的长问卷。
- Planner 使用“通用框架 + 模型编排”：代码提供稳定的单元类型和学习循环，模型结合目标、画像、时间和来源生成具体主题、顺序、时长与理由。
- Planner 输出计划草案，用户确认后才创建正式计划。模型失败时显示真实失败原因，允许重新生成或人工调整，不生成伪造计划。

任意工程技术都可以创建计划。没有匹配实验环境的单元必须标记为 `external` 或 `guided`，不伪装成可运行 Lab。

## 5. 第三阶段：外部实践、来源与反馈

### 外部实践

- 用户可以从自己的编辑器、终端或项目中操作，再回传代码、日志、配置、报错和结果。
- Web 不执行用户本地命令；CLI 自动采集作为用户明确授权的本地连接器，后续再接入。
- 通用 Activity Coach 负责目标澄清、证据追问、实践反思和下一步建议；MySQL 专属 Coach 继续保留自己的 Lab 完成条件。
- 所有外部输入都标记来源和验证状态，进入同一活动事件链，供 Tutor、掌握判断和写作使用。

### 知乎来源

- 来源从“实践中的 Tutor 参考”扩展为“学习单元级来源编排”。
- 每条来源记录所属单元、推荐理由、支撑的概念、作者、链接和检索时间。
- 知乎 CLI Provider 继续使用配置化可执行路径；不可用时展示真实状态，不伪造来源。
- 来源可以固定到当前活动，并进入后续文章证据包；知乎观点和用户实测始终分开表示。

### 掌握与调整

- 从活动证据、检查点结果和 Tutor 轨迹中提炼能力状态、薄弱点和时间偏差。
- 新增 `PlanAdjustment`，包含触发证据、影响单元、原安排、新建议和解释理由。
- 调整采用“系统提出、用户确认”：只有用户接受后才更新未开始单元，已完成单元永不回退。
- 周复盘展示计划与实际、掌握变化、待确认调整和下一周建议。

## 6. 第四阶段：验证通用性与扩展案例

第一个异质案例选择“Kafka 消费延迟”，在计划反馈能力稳定后进入路线。

- 第一版 Kafka 使用 `external` 活动与结构化日志、指标和配置快照，不增加新的常驻 Docker 资源。
- 验证事件模型、Tutor、知乎来源、证据索引、写作和计划调整不依赖 SQL 或 MySQL。
- Kafka 案例稳定后，再评估是否建设受控 Kafka Lab；Redis、一致性和 Kubernetes 排障均复用同一案例协议。
- 案例通过 manifest 描述目标、阶段、输入、可接受证据、完成条件和推荐来源；领域规则只能由案例适配器提供。

## 7. 第五阶段：知乎与长期产品能力

- 完成知乎 OAuth 身份绑定，采用“绑定当前 learnerId”的迁移方式，不重新创建学习身份。
- 文章生成、编辑和人工确认完成后，支持写入知乎草稿；真实发布必须由用户明确授权。
- 多计划支持创建、切换、归档和历史查看；默认只突出一个 active plan。
- 真实任务可以从当前单元创建临时分支，完成后记录对主计划的影响并提供回归动作。
- 在身份授权稳定后再做跨设备同步、收藏画像和长期学习历史迁移。

## 8. 数据与并发边界

- 新增 `learning_activities`、`profile_evidence`、`diagnostic_turns` 和 `plan_adjustments`；迁移只通过 `npm run db:migrate` 人工执行。
- 计划概览、单元、活动、画像和调整接口全部校验 `X-Learner-Id`，不得仅凭资源 ID 访问。
- 建立 `(learner_id, updated_at)`、`(plan_id, position)`、`(plan_unit_id, status)`、`(activity_id, created_at)` 和 `(plan_id, status, created_at)` 索引。
- 概览和复盘使用聚合或批量查询，禁止按单元、事件或证据逐条 N+1 查询；高频查询使用 `EXPLAIN` 检查索引命中。
- 同一 plan unit 同时只允许一个 active activity；计划调整使用 revision 乐观锁，防止并发重复接受或覆盖用户修改。
- Lab 继续沿用现有 run 锁、租约和 FIFO 调度；通用活动不能绕过 Lab 的资源边界。

## 9. 验收顺序

1. 用真实 ProductPlan 替换前端 Mock，并完成“目标 -> 计划 -> MySQL 实践 -> 返回计划”。
2. 加入 PDF 简历解析、画像确认和少量动态诊断。
3. 完成通用 Planner、计划版本和用户确认式调整。
4. 完成 external activity、上下文回传、通用 Tutor 和学习单元级知乎来源。
5. 用 Kafka 消费延迟案例完成一次跨领域验证。
6. 最后接入知乎 OAuth、草稿发布、多计划和真实任务分支。

每个阶段都必须通过后端测试、前端类型检查、构建和 1440px/1024px 浏览器验收后，才能进入下一阶段。任何新案例都不能以牺牲真实计划主线为代价提前铺开。

## 10. 默认决策

- 近期首要目标：贯通真实学习主线，而不是优先扩充案例数量。
- 学习目标：任意工程技术可生成计划；是否有 Lab 由单元实践方式决定。
- Planner：通用框架加模型编排，不采用完全自由生成或固定技术目录。
- 简历：PDF 上传、成熟库提取、删除原件、保留解析结果和用户确认后的画像依据。
- 身份：继续使用单浏览器 learnerId，OAuth 与跨设备同步延后。
- 计划调整：系统提出建议，用户确认后生效。
- 异质案例：Kafka 消费延迟优先于 Redis 和 Kubernetes。
- 知乎：先做学习节点来源编排，再做 OAuth 收藏和发布。
