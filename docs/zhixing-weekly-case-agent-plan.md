# 知行本周实现计划：案例构建 Agent 与 Python 实践底座

版本：v0.1  
周期：2026-09-07 至 2026-09-13  
目标：在不破坏现有 MySQL Lab、规划路线和 Tutor 闭环的前提下，完成第一条通用案例实践链路。

## 1. 本周确认的方向

本周不再把 Agent 设计成“环境规划 Agent”。这个命名和职责划分会导致先选择容器、再寻找学习任务，用户体验和学习逻辑都不自然。

正确的职责关系是：

```text
路线节点
  -> Case Builder Agent 构建一个具体工程案例
  -> 平台匹配基础运行环境
  -> 用户在 Docker 工作区中完成案例
  -> Tutor 读取真实过程继续引导
  -> 实践证据、路线进度和文章沉淀
```

Docker 对用户来说只是运行底座。用户看到的核心对象是一个有背景、目标、起始材料、任务推进和验证方式的案例。

本周的第一条案例使用 Python，先验证“案例生成 -> 环境启动 -> 代码修改 -> 测试 -> 证据沉淀”的完整链路。现有 Fastify + TypeScript API 不改写为 Python；Python 只作为第一个学习运行时模板。

## 2. 本周完成标准

用户从路线图的一个 Python 能力节点进入后，可以完成：

```text
打开节点
  -> 生成或读取一个 Python 案例
  -> 查看案例背景和当前任务
  -> 启动 python-pytest 工作区
  -> 在终端执行测试
  -> 编辑或上传文件
  -> 再次执行测试
  -> 保存命令、输出和文件变化
  -> Tutor 根据真实输出进行下一步引导
  -> 完成案例并回到路线图
```

本周不要求实现所有语言和中间件，也不要求 Agent 自由生成 Dockerfile。只要 Python 案例在受控基础环境中稳定完成，就算本周目标达成。

## 3. 能力边界

### 3.1 Case Builder Agent 负责什么

Case Builder Agent 根据当前路线节点、知识卡、学习者画像摘要和已有实践反馈，生成一个可执行的案例草案：

- 案例标题、背景和用户在案例中的角色；
- 本次要完成的实际功能或问题修复；
- 起始代码、配置、fixture 和测试文件；
- 分阶段任务以及每阶段要观察的现象；
- 推荐命令和验证命令；
- Tutor 需要关注的关键节点；
- 本次实践应沉淀的原始证据。

Agent 可以构建业务问题和代码任务，但不能直接调用 Docker、执行宿主机命令或决定宿主机挂载。

### 3.2 运行底座负责什么

运行底座只负责把案例放入平台支持的模板中执行：

- 选择基础镜像；
- 创建短期工作区；
- 写入 starter files 和测试；
- 提供终端、文件上传和命令输出；
- 保存执行事件和结果；
- 处理重置、结束、租约和清理。

运行底座不理解案例内容，也不替 Agent 判断用户是否掌握知识。

### 3.3 Tutor 负责什么

Tutor 接收当前 `CaseSpec`、用户输入、文件变更、命令和测试输出，负责：

- 解释当前观察到的现象；
- 追问用户的判断；
- 给出分级提示；
- 帮助用户定位测试失败；
- 引导用户完成下一步验证。

Tutor 不替用户修改文件、不直接执行命令，也不根据一句聊天内容伪造案例完成状态。

## 4. 案例模型

本周新增通用案例模型，但保留现有 MySQL PracticeRun 的兼容路径。实现前先核对当前表结构、索引和 PracticeRun 的所有调用方，不猜测字段。

### 4.1 CaseSpec

Agent 输出受 Zod 校验的结构化案例规格，第一版字段如下：

```ts
type CaseSpec = {
  title: string
  scenario: string
  learningGoal: string
  difficulty: 'introductory' | 'applied' | 'advanced'
  environment: {
    templateKey: 'python-pytest-v1'
    services: string[]
  }
  starterFiles: Array<{ path: string; content: string }>
  tasks: Array<{
    key: string
    instruction: string
    recommendedCommands: string[]
    expectedObservation: string
  }>
  verification: {
    commands: string[]
    successSignals: string[]
  }
  tutorContext: {
    concepts: string[]
    likelyMisconceptions: string[]
    evidenceToNotice: string[]
  }
}
```

结构校验只解决“能否被运行平台执行”的问题，不增加“证据不足就阻塞”“必须覆盖若干章节”等内容质量门槛。模型可以生成不同叙事和任务顺序，只要引用了受支持的运行时模板且文件、命令结构完整即可进入工作区。

### 4.2 持久化边界

本周优先增加两类持久化记录：

- `learning_cases`：案例版本、路线节点、输入指纹、生成状态、CaseSpec 快照和创建时间；
- `case_generation_jobs`：案例生成请求、模型、状态、失败原因、重试次数和完成时间。

已有案例和实践记录不覆盖。相同路线节点、相同输入指纹和相同生成请求必须幂等返回已有结果。

实践执行记录优先复用已有事件与 Artifact 体系；只有在确认当前 PracticeRun 无法承载通用案例字段后，才新增 `case_runs` 或独立 `environment_runs`。本周不为了“通用”提前复制一套实践、Tutor 和证据模型。

## 5. Python 第一版运行模板

### 5.1 模板内容

`python-pytest-v1` 使用平台预置镜像和固定启动协议：

- Python 3.13；
- pytest；
- 工作目录 `/workspace`；
- 测试命令默认为 `pytest -q`；
- 案例文件由平台写入工作目录；
- 运行结果统一回传为 command、stdout、stderr、exitCode、duration 和文件变更。

本周不开放任意基础镜像、任意 Dockerfile 或任意 Compose 文件。依赖优先随模板预装，避免把 Demo 成功与现场网络、pip 镜像和第三方包可用性绑定。

### 5.2 工作区交互

工作区采用当前实验室的终端风格：

- 左侧显示案例任务和当前步骤；
- 中间是终端和命令输出；
- 文件列表按需展开；
- 支持上传有限大小的案例文件；
- 测试输出可展开并保存为证据；
- 支持重置到案例初始状态；
- Tutor 位于右侧或抽屉，不挤压终端主区域。

不新增复杂 IDE。第一版只需让用户能清楚完成“读代码 -> 执行测试 -> 修改 -> 再执行”的循环。

## 6. 支持能力目录

能力目录可以一次性列出未来方向，但实现状态必须显式区分，不能让路线图把未实现的能力显示成可用环境。

| 能力 | 类型 | 本周状态 | 后续状态 |
| --- | --- | --- | --- |
| Python + pytest | 语言工作区 | `available` | 持续扩充案例 |
| Go | 语言工作区 | `planned` | 添加 go test 模板 |
| Java | 语言工作区 | `planned` | 添加 JDK + Maven/Gradle 模板 |
| Rust | 语言工作区 | `planned` | 添加 cargo test 模板 |
| C++ | 语言工作区 | `planned` | 添加 CMake + test 模板 |
| Redis | 服务依赖 | `planned` | 先做 Python/Go + Redis 组合 |
| Kafka | 服务依赖 | `planned` | 单节点 KRaft 模板，单独评估资源 |

这份目录是能力注册表，不是一次性承诺。Case Builder 只能选择状态为 `available` 的模板；遇到未支持能力时，生成“待实施案例草案”或明确提示当前不可启动，不生成伪造的实验入口。

## 7. 本周任务拆解

### 第 1 天：契约和运行时边界

- 核对现有路线节点、PracticeRun、Artifact、PracticeEvent、Tutor 输入和 Lab 生命周期表结构；使用 CodeGraph 查询调用链和影响范围。
- 确定 `CaseSpec`、案例状态和生成任务状态。
- 建立 `python-pytest-v1` capability registry，先用代码配置，不做复杂后台管理页。
- 确定工作区创建、命令执行、文件上传、重置和结束的接口契约。
- 写出一个人工固定 CaseSpec fixture，先不依赖模型即可运行。

交付物：类型、状态图、接口草案、固定 Python 案例 fixture。

### 第 2 天：案例构建 Agent

- 新增 Case Builder Provider，复用当前模型配置和超时日志机制。
- 设计案例生成提示词：强调构建实际问题、起始材料、任务和测试，不提 Docker 操作。
- 使用结构化 JSON 输出并进行 Zod 校验。
- 增加输入指纹、幂等、超时、失败和重试记录。
- 对模型返回未知模板、空文件、危险路径和非法命令做结构性拒绝。
- 增加“模型不可用时仍可使用固定 fixture”的开发模式，但不把固定内容伪装成模型生成结果。

交付物：`CaseBuilderService`、生成任务接口、Agent 单元测试和固定 fixture 回退路径。

### 第 3 天：Python 工作区后端

- 实现 Python 模板解析和工作区创建。
- 将 starter files、测试和任务写入工作目录。
- 接入终端命令执行和输出事件。
- 保存文件变更、命令、输出和测试结果到现有实践证据链。
- 实现重置、结束、租约和失败重试。
- 让 Tutor 请求携带当前 CaseSpec 和最近的终端证据。

交付物：后端可创建 Python 工作区，运行 `pytest -q`，并读回完整执行记录。

### 第 4 天：前端案例工作区

- 从路线节点进入案例详情和“开始实践”。
- 展示案例背景、目标、任务和验证方式；不显示 Dockerfile 或基础设施细节。
- 将终端、文件操作、测试结果和 Tutor 组织成一个工作区。
- 终端输出使用独立滚动容器，避免页面无限向下延伸。
- 文件上传失败、命令失败、环境不可用和 Agent 失败都显示真实状态。
- 保持当前 editorial technical 风格、左侧导航和 1024px/1440px 布局。

交付物：浏览器可以完成 Python 案例，不需要直接调用 Docker API。

### 第 5 天：闭环验收和扩展准备

- 验证固定 fixture 与模型生成 CaseSpec 的两条路径。
- 验证刷新、重置、结束、重复启动和生成重试。
- 验证 Tutor 能看到测试输出和文件变化，且没有越权执行动作。
- 验证案例完成后路线节点状态正确更新，原始证据和写作入口不受影响。
- 运行后端测试、构建、前端 typecheck、测试和构建。
- 运行 CodeGraph 重建并检查新增服务的影响范围。
- 记录 Python 模板后续扩展 Go、Java、Rust、C++、Redis、Kafka 所需的差异，不在本周提前实现。

交付物：一条可以重复演示的 Python 案例闭环和下一阶段扩展清单。

## 8. 最小运行边界

本周不做企业级容器安全体系，但因为执行的是用户可上传和生成的代码，以下边界仍然是基础运行条件：

- 工作区不能访问 Docker socket；
- 不能挂载宿主机目录、产品 SQLite、MySQL 数据或服务密钥；
- 不使用 `privileged`、host network 或宿主机端口；
- 单个工作区有执行时长、内存、磁盘和上传大小上限；
- 到期或结束后清理工作区；
- 浏览器只能通过 API 获取终端输出。

Demo 阶段可以暂不引入 gVisor、Firecracker、Kubernetes 和复杂镜像签名，但不能让案例容器直接获得宿主机控制权。若仍使用当前线上主机，至少把工作区进程和产品服务权限分开；更稳妥的方式是准备单独的 sandbox worker。

## 9. 测试与性能要求

### 后端

- CaseSpec 合法生成、非法 JSON、未知模板、非法路径和非法命令；
- 相同输入指纹和 `clientRequestId` 幂等；
- Agent 超时、429、空响应和重试；
- fixture 创建工作区、执行测试、保存输出和重置；
- 终端证据可以被 Tutor 读取；
- 同一案例重复启动不会产生重复运行；
- learner 所有权校验和历史案例读取；
- 服务重启后生成任务与工作区状态可恢复或明确结束。

### 前端

- 案例加载、生成中、生成失败、重试和固定案例入口；
- 终端输出持续追加且只在终端区域滚动；
- 文件上传、测试失败、测试通过和重置；
- Tutor 可以看到当前执行证据；
- 刷新后恢复当前案例和工作区状态；
- 1024px 与 1440px 不出现横向溢出和无限页面延展。

### SQL 与请求性能

- 所有新增手写 SQL 参数化；
- 案例详情、生成任务和工作区状态按索引读取；
- 禁止按任务、文件或事件循环查询数据库形成 N+1；
- 高素材实践的证据读取使用批量查询；
- 对案例列表、当前工作区和事件分页查询执行 `EXPLAIN QUERY PLAN`。

## 10. 不在本周实现

- 收藏分析与收藏驱动专题生成；
- 任意 Dockerfile、Compose 或自定义镜像构建；
- 浏览器直接连接 Docker daemon；
- Go、Java、Rust、C++、Redis、Kafka 的实际模板；
- 任意语言和服务的自由组合；
- 完整 IDE、断点调试和多容器可视化编排；
- 企业级沙箱、Kubernetes 调度和跨机器资源管理。

收藏分析仍然有价值，但应在案例平台能承接“收藏 -> 主题 -> 实践案例”之后推进。否则只能生成阅读专题，无法完成用户真正想要的“收藏变成行动”。

## 11. 本周结束后的决策门

只有以下条件全部满足，才进入 Go/Java 和 Redis 扩展：

1. Python 案例可以从路线节点重复启动并完成；
2. Agent 生成的是案例，不是容器指令；
3. 终端、测试输出和文件变化进入 Tutor 与证据链；
4. 重置、结束、刷新恢复和失败重试稳定；
5. 运行平台不需要修改现有 MySQL Lab 的完成判定；
6. 线上服务与案例工作区没有共享宿主机控制权限。

达到条件后，下一周优先添加 Go 或 Java 其中一个语言模板，再添加 Redis 组合。Kafka 单独排期，因为它是独立服务和资源问题，不应作为普通依赖包顺手接入。
